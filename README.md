# caelestia-fedora

A Fedora Atomic image running the [Caelestia](https://github.com/caelestia-dots) desktop, built from source and published as a signed ostree image.

## Sources of truth

Two upstream projects define this image. Neither is ours to maintain.

| | |
|---|---|
| [wayblueorg/wayblue](https://github.com/wayblueorg/wayblue) | The base image. A Fedora Atomic desktop with Hyprland, SDDM, portals and NVIDIA support already working. We layer on top of it and never rebuild it. |
| [blue-build/template](https://github.com/blue-build/template) | How the image is built. BlueBuild turns `recipes/recipe.yml` into a Containerfile and commits it to ostree with cosign signing. |

Everything specific to Caelestia lives in `recipes/recipe.yml` (generated by `./build.py recipe`) and `files/scripts/build-from-source.sh` (generated by the same command). Both are generated. Do not hand edit them.

The single most important consequence of BlueBuild: **it derives the registry path from the recipe's `name:` field.** There is no `IMAGE_NAME` workflow input. Two branches that share a name overwrite each other's `:latest`.

## Branches

| Branch | Base image | Published to |
|---|---|---|
| `main` | `ghcr.io/wayblueorg/hyprland-nvidia-open` | `ghcr.io/lovel33t/caelestia-fedora` |
| `hyprland` | `ghcr.io/wayblueorg/hyprland` | `ghcr.io/lovel33t/caelestia-fedora-hyprland` |

Both are built by the same workflow file, kept in sync on purpose. The only differences between them are `base_image`, `base_image_version` and `image_name` in `config/packages.json`, plus the image name and remote in `.github/workflows/build.yml` and `files/scripts/firstboot-setup.sh`.

Switching base is a three field change in `config/packages.json`:

```json
"base_image": "ghcr.io/wayblueorg/hyprland",
"base_image_version": "44",
"image_name": "caelestia-fedora-hyprland"
```

Then re-audit against the new base before pushing:

```bash
./build.py audit
```

`already_in_base` and `remove_from_base` in `packages.json` describe the base image specifically. They are tuned for whichever base you last audited and need rechecking after a switch.

## GPU support

**Only `hyprland-nvidia-open` is supported and tested.** That is the open kernel module stack, which needs Turing (GTX 16xx / RTX 20xx) or newer.

Older cards need the **closed** `nvidia` module, which this image does not ship or test. Rather than guess at it, we would rather say so plainly: **fork this repo and add it.** The pieces you need are a base image change and a kernel argument change, nothing else. If you do it, the `hyprland` branch is a working example of how to vary the base without forking the build.

Do not open a pull request asking for closed-module support here without a working branch behind it.

## Pushing

```bash
./build.py resolve --verify     # confirm the lock has not drifted
./build.py audit                # packages still resolve on the base
./build.py recipe               # regenerate recipe.yml + build-from-source.sh
git add -A && git commit -m "..."
git push origin main
```

`resolve --verify --strict` fails the build if any pinned revision moved. The lock in `build/deps.lock.json` is what CI builds from.

CI compiles everything from source on GitHub runners. Your machine does not build anything unless you run `./build.py build` yourself.

Watch a build without pasting logs:

```bash
./ci-log.sh          # run status, job steps, and error lines from the log
```

It needs a fine-grained token with `Actions: Read-only` and `Contents: Read-only`, stored at `~/.config/caelestia-agent/token` (mode 0600, outside the repo). Without it the API refuses to return job logs at all.

The build publishes `latest` plus an immutable `<commit>-44` tag. Prefer the pinned tag when you need to be certain which build you got.

## Installing

Start from a normal Fedora Silverblue or other Atomic install, then rebase onto this image.

Rebase to the unsigned image first. This installs the signing policy the signed image needs:

```bash
sudo rpm-ostree rebase ostree-unverified-registry:ghcr.io/lovel33t/caelestia-fedora:latest
sudo systemctl reboot
```

Then rebase to the signed image:

```bash
sudo rpm-ostree rebase ostree-image-signed:docker://ghcr.io/lovel33t/caelestia-fedora:latest
sudo systemctl reboot
```

The first boot provisions the account you already have. You installed Silverblue or Kinoite and chose a username before rebasing, so nothing here creates a user. It sets zsh as the login shell, grants that account passwordless sudo, deploys the dots, seeds a wallpaper, and enables the daily update timer. It runs once, guarded by `/var/lib/caelestia/provisioned`.

To provision a different account, set `CAELESTIA_USERNAME` for `caelestia-firstboot.service` in a drop-in.

For a card that needs the closed NVIDIA module, this image will not work. See GPU support above.

Check what you ended up with:

```bash
rpm-ostree status
caelestia-update --status
```

## Layered packages

The image layers these on every deployment, through `files/etc/ostree/prepare-root.d/00-caelestia-layering.sh`:

```
e2fsprogs  util-linux  gdisk  smartmontools  neovim
```

Those are Fedora package names, not command names. There is no `nvim` package; the editor is `neovim`.

Layering is how a package survives a rebase. `rpm-ostree install foo` adds a package to the running deployment only, and it is gone after the next update. Anything in `prepare-root.d` is reapplied on every deployment.

Add more by editing that script, not by installing them by hand.

## Verifying a release

```bash
cosign verify --key cosign.pub \
  ostree-image-signed:docker://ghcr.io/lovel33t/caelestia-fedora:latest
```

`cosign.pub` is committed at the repo root. The private key never enters the repo and is stored as the `SIGNING_SECRET` GitHub Actions secret.

## Updating machines

The image configures its own update path on first boot: `caelestia-firstboot.service` writes an ostree remote and enables `caelestia-upgrade.timer`, which checks daily at 00:00 local time. Updates are staged, never applied unattended.

```bash
caelestia-update              # report, and stage if newer
caelestia-update --check      # report only
caelestia-update --status     # what is booted right now
systemctl reboot              # apply what is staged
```

The script reads its image path from the ostree remote, so the same binary is correct on the NVIDIA and non-NVIDIA images without being told which.

Two digests appear in its output. The `index` digest is what the tag points at. The `platform` digest is the `linux/amd64` child that actually gets deployed. Compare `platform` with `deployed`.

Do not rebase to a pinned `<commit>-44` tag on a machine you intend to keep updating. `rpm-ostree rebase <ref>` records that exact ref as the deployment origin, which permanently pins the machine to that one build. Rebase to `:latest`.

## Layout

```
build.py                     stage orchestrator and generator
ci-log.sh                    CI status and log helper
config/
  packages.json              Fedora packages, COPRs, base image, image name
  sources.json               every upstream source, all SHA or digest pinned
files/
  etc/                       systemd units, presets, udev rules
  scripts/                   build-from-source.sh is generated; the rest are not
  usr/bin/                   caelestia-update and the caelestia-shell wrapper
recipes/recipe.yml           generated. what BlueBuild actually builds
```

Generated files say so in their first lines. Regenerate with `./build.py recipe` rather than editing them.
